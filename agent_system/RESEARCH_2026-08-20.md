# External capability research — 2026-08-20

This file records current candidates for the agent/MCP composition layer. It is a research ledger, not permission to install or trust third-party code.

## Adopt now

### Pydantic AI
Status: ADOPT AS PRIMARY PYTHON AGENT HARNESS CANDIDATE.

Why: model-agnostic agent framework, local-first MCP capability, explicit MCP connection/read timeouts, usage limits, multi-agent delegation/graph control, human approval hooks, durable execution, and progressive tool/capability exposure.

Primary sources:
- https://github.com/pydantic/pydantic-ai
- https://github.com/pydantic/pydantic-ai/blob/main/docs/capabilities/mcp.md
- https://github.com/pydantic/pydantic-ai/blob/main/docs/timeouts.md
- https://github.com/pydantic/pydantic-ai/blob/main/docs/multi-agent-applications.md

### Qwen-Agent
Status: ADOPT AS OPTIONAL LOCAL/OPEN-WEIGHT SECOND ENGINE.

Why: actively maintained, Qwen 3.5-era framework with function calling, memory, RAG, code interpreter, BrowserQwen examples, and MCP cookbook/config support. It can dynamically load MCP servers through `mcpServers`. The bundled code interpreter is not sufficient as a production security boundary by itself.

Primary sources:
- https://github.com/QwenLM/Qwen-Agent
- https://github.com/QwenLM/Qwen-Agent/blob/main/qwen-agent-docs/website/content/en/guide/get_started/configuration.md

### Ollama
Status: ADOPT AS DEFAULT LOCAL OPENAI-COMPATIBLE MODEL ENDPOINT CANDIDATE.

Why: local model serving, OpenAI-compatible `/v1/chat/completions` and `/v1/responses`, tool calling, reproducible-output support, and no cloud dependency for ordinary local inference. Compatibility is partial; do not assume every OpenAI Responses feature exists.

Primary sources:
- https://github.com/ollama/ollama/blob/main/docs/api/openai-compatibility.mdx
- https://github.com/ollama/ollama/blob/main/docs/capabilities/tool-calling.mdx

### MCP
Status: ADOPT AS TOOL/AGENT INTERCHANGE BOUNDARY.

Why: reduces provider lock-in and lets the model-facing runtime discover narrow tools without receiving generic shell/cloud authority. Prefer local stdio or loopback transports for private repositories and sensitive corpora.

Registry:
- https://registry.modelcontextprotocol.io/

## Integrate selectively

### Google Agent Development Kit (ADK)
Status: INTEROP CANDIDATE.

Why: open-source code-first toolkit with multi-agent support, A2A integration, and the ability to expose an entire ADK agent as a standard MCP server (`to_mcp_server`). This is useful for making an agent portable across Codex, IDEs, and other MCP hosts without coupling the host to ADK.

Primary sources:
- https://github.com/google/adk-python
- https://github.com/google/adk-python/blob/main/docs/guides/tools/mcp_tool/agent_to_mcp/index.md

### LiteLLM
Status: OPTIONAL PROVIDER GATEWAY.

Why: self-hosted OpenAI-compatible gateway for many model providers plus an MCP bridge/gateway. It can become the narrow model-provider abstraction when multiple cloud/local backends are genuinely in use. Do not deploy a gateway merely to add abstraction before there is a second backend to route.

Primary source:
- https://github.com/BerriAI/litellm

### goose (Agentic AI Foundation)
Status: EVALUATE AS COMMODITY LOCAL CODING/WORKFLOW AGENT.

Why: open-source local desktop/CLI/API agent, many model providers, and broad MCP extension support. Potentially useful as a commodity execution/client surface rather than rebuilding another coding-agent shell.

Primary source:
- https://github.com/aaif-goose/goose

Status: DISCOVERED, NOT TRUSTED/INSTALLED.

## Defer

### Microsoft Agent Framework
Status: DEFER PYTHON INSTALLATION UNTIL MCP 2.x TRANSITION SETTLES.

Why: strong production-oriented multi-agent/workflow features, MCP examples, background agents, A2A sessions, and durable patterns. However, the Python package currently has an active MCP 2.x migration issue/PR and historically pins `mcp>=1.24,<2`. Introducing it into the same environment as MCP 2.x today risks dependency conflict.

Primary sources:
- https://github.com/microsoft/agent-framework
- https://github.com/microsoft/agent-framework/issues/7446

## Composition rules produced by this pass

1. Several agents should be independent roles with explicit non-result states, not four prompts whose failures are silently averaged.
2. Every agent/model/tool call has a bounded timeout.
3. MCP tools are narrow and capability-specific; no generic shell or ambient credential endpoint.
4. Local OpenAI-compatible model serving is the baseline second-model path; cloud providers are replaceable.
5. Tool discovery is progressive. Do not expose hundreds of MCP tools to every turn.
6. Deterministic source/hash checks remain outside model judgement.
7. External MCP servers remain DISCOVERED until source, release provenance, permissions, network behavior, and failure mode are reviewed.
8. Framework adoption must reduce bespoke code or unlock a blocked capability. Dependency accumulation by itself is not progress.
